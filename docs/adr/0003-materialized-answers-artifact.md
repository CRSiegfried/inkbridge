# ADR-0003: Response state as a materialized answers artifact, monitoring delegated

Status: Accepted
Date: 2026-07-21

## Context

Analysis 0017 (unpublished) proposed
two reactive command families to close the agent's document loop: `watch` /
`wait` (finding 2 — a poll/follow loop that emits an event per state
transition, and a blocking `wait --until responded`) and a `collect` ack-split
(finding 3 — make reading pure, move the ledger acknowledgement into an
explicit `ack`). Both are downstream of the read-never-mutate principle in
[ADR-0002](0002-agent-facing-cli-contract.md).

Designing them out, the machinery grew faster than the value. `watch` needs
its own "already-emitted-this-transition" cursor kept *separate* from the
ledger ack (or emitting an event would mutate state), i.e. a second state
store. `wait` bakes a blocking poll-and-sleep policy into the CLI. The
ack-split adds an `ack` verb and forces a decision about what read view
`collect` should default to (cell-level vs. question-level) purely to protect
against reads advancing the ledger.

Meanwhile the semantic result already has a single pure producer:
`answers.resolve_answers` over the readback decode (built on ADR-0002 as the
first contract command). The observation that reframes all of it: **response
state can be a file.** If the resolved answers are materialized to disk, a read
is just parsing that file — pure by construction — and monitoring is something
general-purpose tools (the agent's own loop, `fswatch`, cron) already do well,
against that file, without a bespoke follow loop in our CLI.

One fact constrains the design and must be stated plainly: **there is no free
freshness.** The device syncs a `.pdf.mark` back through the private cloud,
which gives us no change notification — the current ink state is only knowable
by polling (`status` / `check_entries`), and the *local* mark only changes when
we pull it. So a materialized artifact cannot update itself from device ink; it
is (re)generated by a poll-driven refresh. The agent already runs on a loop, so
that refresh is not new work — but "auto-updates when files change" is only
true for the local artifact, never for remote ink.

## Decision

We will represent a dispatched document's response as a **materialized answers
artifact** — a per-document sidecar file holding the `answers.v1` payload that
`resolve_answers` produces — and delegate monitoring to tooling outside the
CLI, rather than building `watch` / `wait` or a `collect` ack-split.

Concretely:

1. **`collect` writes the sidecar.** `collect <doc>` pulls the latest
   `.pdf.mark` and writes `<doc>.answers.json` (the `answers.v1` document)
   beside the pulled mark, reusing `resolve_answers` — no second resolver. The
   sidecar carries the **provenance** of the ink it reflects: the `mark_md5`
   it was derived from. `collect` no longer acknowledges as a side effect of
   reading.

2. **Reads are pure file reads.** Consuming response state is parsing the
   sidecar. The `answers` command remains the on-the-fly reader/renderer
   (resolve a manifest + mark directly, for ad-hoc inspection or when no
   sidecar exists yet); the sidecar is the persisted, watchable form of the
   same payload. Either way nothing mutates ledger, remote, or local input.

3. **Staleness is a provenance diff, not an event.** A consumer decides
   "is this current?" by comparing the sidecar's `mark_md5` against the current
   remote mark md5 that `status` already reports — the same ink-signal the
   ledger join uses. That replaces what `watch`/`wait` were to provide.

4. **We will not build `watch`, `wait`, or an ack-on-read split.** Reactive
   monitoring is delegated: the agent's loop (or an external file-watcher /
   scheduler) refreshes via `collect` and reacts to the sidecar. Freshness
   comes from that poll; the CLI stays a set of composable one-shot verbs.

Retiring a document (`close`, Analysis 0017 finding 3's terminal verb) remains
a separate, still-deferred concern — it is about ending a doc's lifecycle, not
about read hygiene, and is not decided here.

## Consequences

**Easier.** Far less machinery: no follow loop, no second transition cursor, no
`ack` verb, no blocking-poll policy in the CLI. Response state is inspectable on
disk with any tool. Reads are trivially safe, so the whole read/mutation-hygiene
concern that motivated the ack-split disappears. One resolver
(`resolve_answers`) feeds both the live command and the persisted sidecar, so
the two output shapes cannot drift. Monitoring composes with whatever the
operator already runs.

**Harder / the costs.** Freshness is pull-driven: a consumer that never polls
sees a stale sidecar, and nothing in the filesystem will tell it otherwise — the
`mark_md5` provenance is what makes staleness *detectable*, but detecting it
still requires a `status`/`collect` poll. We give up in-CLI blocking semantics:
a linear "wait until responded, then act" script must now poll-and-sleep around
our verbs itself, rather than calling one `wait`. Concurrent refreshes of the
same doc are last-write-wins on the sidecar (acceptable — the payload is a pure
function of the mark, so racing writers converge, but two agents collecting the
same doc is not coordinated). And `collect`'s output changes character: it now
yields the semantic artifact rather than the cell-level table it printed before
(cell-level stays available via `readback`).

**Giving up.** First-class reactive monitoring as a CLI feature. We are betting
that "state as a file + a general-purpose watcher/loop" covers the reactive use
cases well enough that a bespoke `watch`/`wait` is not worth its state-machine
and its second cursor. If a consumer genuinely needs push-style eventing this
does not provide it — that consumer builds on the poll primitives we expose.

## Alternatives considered

- **`watch` / `wait` as first-class commands** (Analysis 0017 finding 2):
  rejected. They reimplement, inside the CLI, what a materialized file plus a
  general-purpose watcher or the agent's existing loop already do, and `watch`
  drags in a second state cursor kept separate from the ledger ack. The value
  over "write a file, let something watch it" did not justify the machinery.
- **`collect` read/write (ack) split** (Analysis 0017 finding 3): rejected *as
  a read-hygiene mechanism*. Its whole purpose was to stop a read from advancing
  the ledger; materializing state as a file makes reads pure by construction, so
  the hazard is gone and the extra `ack` verb is unnecessary. (An explicit
  terminal `close` for retiring a doc is a different concern and remains open.)
- **One aggregate answers file across all docs** (ledger-style): rejected in
  favor of a per-doc sidecar mirroring how `compose` already drops
  `.manifest.json`. A directory of sidecars is just as watchable and avoids a
  single-file write-contention hotspot as more docs are dispatched.
- **Lazy resolve-on-read only, no persisted file** (what the `answers` command
  does today): kept, but not sufficient alone. On-the-fly resolution is right
  for ad-hoc inspection, but an agent loop and external watchers want a stable,
  provenance-stamped artifact on disk to diff against — so `collect` persists;
  the command still resolves live. Not either/or.
